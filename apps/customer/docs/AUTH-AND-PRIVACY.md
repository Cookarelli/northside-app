# Prompt 2: identity and privacy implementation

This is an implemented local foundation, not a claim of hosted Supabase or real OAuth verification. No credentials are in this repository. Staff invitations, provider login and private files remain disconnected until setup below is completed.

## Enforcement path

1. Customer login starts with a same-origin POST. The server discovers authentication metadata from the configured Northside shop, checks the exact pinned issuer and HTTPS endpoint allowlist, then uses openid-client 6.8.8 with confidential client authentication, S256 PKCE, random state and nonce. The one-time attempt is encrypted in PostgreSQL and addressed by a random secure HttpOnly cookie. Callback consumes the attempt atomically before exchange. The library checks signed ID tokens, issuer, audience, expiry, subject, state and nonce, including JWKS signature verification. Only exact allowlisted relative return paths are accepted.
2. A verified Shopify subject maps through tenant + shop + provider + subject to one internal customer UUID. No email lookup creates or merges an account, and no query parameter chooses the customer. Identity creation uses a database transaction and advisory lock to avoid duplicate accounts. Northside is the only application tenant; the second tenant exists only in tests.
3. Supabase staff sign-in verifies a one-time email token on the server, then calls `auth.getUser(access_token)` and looks up an existing active membership by its verified Supabase user UUID. Passwordless login uses `shouldCreateUser:false`. No client-supplied role or email match creates membership. There is no public staff signup, default admin or customer Supabase login.
4. The application issues a 256-bit random `__Host-ns_session` cookie with Secure, HttpOnly, SameSite=Lax, Path=/ and an eight-hour absolute expiry. PostgreSQL stores only its SHA-256 lookup hash. Access/refresh/ID tokens are AES-256-GCM encrypted with a server environment key and session-hash associated data. OAuth attempts expire in five minutes. No tokens go to localStorage, sessionStorage or client props.
5. Every private service refreshes near-expired provider tokens while locking the session row. Successful refresh stores encrypted rotated credentials in the same transaction. Missing refresh tokens or failed/uncertain refresh revoke the local session and require sign-in; no stale authenticated response is served. Eight-hour expiry is not extended. Supabase membership remains checked by the DB even if its provider token has not expired.
6. A separate `northside_runtime` SQL connection starts a transaction, sets only `ns.session_hash` from the validated cookie hash with transaction-local scope, and queries `ns.context()`. The fixed-search-path security-definer function resolves the unexpired, unrevoked session and active membership. It exposes tenant/customer/staff-role only, never tokens. RLS resolves this context independently. Setting a made-up `ns.customer_id`/`ns.tenant_id` does nothing. Browser code cannot connect as this SQL role. Possessing a guessed UUID or Shopify token does not create a Supabase session.
7. Server services also filter by authenticated ownership and require specific staff roles. RLS and composite foreign keys enforce tenant and customer ownership independently, including child records within shared grading batches. Customers cannot read batches or staff notes. Customer event projections omit private reasons and actor IDs. CSV export reuses the same service and escapes formula prefixes.
8. `northside_auth` is a separate trusted server connection with only identity/session/membership grants, used after provider verification. It cannot read operational cards, notes, payouts or ledger tables. Both runtime/auth roles are required to be non-superuser and non-BYPASSRLS. The application rejects migration/admin/service-role SQL credentials. The migration owner has DDL access and is not a request-time credential.
9. Supabase Storage bucket `northside-private` is private. A restrictive policy denies anon/authenticated direct access even if an unrelated permissive policy exists. A server service authorizes the corresponding `ns.file_objects` row before a 60-second signed download. The secret API credential bypasses Storage RLS: protection for that privileged call is the already-authorized object lookup, not an RLS claim. Upload is staff-only, streamed with a 5 MiB cap, a MIME allowlist and signature check. Keys are generated by the server and constrained to the tenant/customer prefix. Metadata is marked ready only after upload succeeds. An upload whose DB commit fails may leave an inaccessible orphan for later cleanup; it is not published or listed.
10. Logout is a same-origin POST that durably revokes the local session and erases stored tokens before clearing both cookies. It attempts provider logout separately; a provider outage does not keep the local session valid. Shopify post-logout target is configured exactly. Responses are private/no-store; logout clears browser cache/storage; a pageshow guard reloads back-forward-cache restorations. Private navigation prefetch is disabled. Prompt 9 adds a service worker caching only six public static assets; authenticated navigation and APIs never enter that cache. Its explicit cross-tab privacy lock complements server revocation. No application logs include tokens, intake notes or payout details. Next incoming-request logging is disabled to avoid OAuth query strings; configure hosting/proxy log redaction too.

The auth connection and runtime connection are trusted server credentials. RLS is defense against authorization mistakes and browser tampering, not a claim that stolen server credentials or arbitrary trusted-server execution is harmless. `ns.context` can use an unguessable session hash but does not accept a free-form tenant or role. Treat session hashes as credentials too.

## Staff permissions

| Role | Scope in Prompt 2 |
| --- | --- |
| owner | Operational reads, private notes/files, audited status append; invite admin/operations/content editor/read only |
| admin | Operational reads, private notes/files, audited status append; invite operations/content editor/read only |
| operations | Operational reads, private notes/files, audited status append and upload; no invitation/role escalation |
| content_editor | Break-content SQL boundary; cannot read customer cards, payouts, exports or private files |
| read_only | Read operational/customer records and exports; no private staff notes or edits |

Initial owner is an invited or confirmed Supabase user selected privately by Steve/Joey and linked using `staff:bootstrap`. It refuses to create another active owner. Owner transfers and full staff-management UI are not silently invented. Supabase invitation email is sent only by an authenticated owner/admin using the invitation UI/API; no invitations were sent during implementation.

## Tables and immutability

Migration 001 defines tenants, customers, scoped Shopify identities, invited staff, encrypted sessions and OAuth attempts, service cases, pooled grading batches, card items, private staff notes, status events, consignment items, files, breaks/spot mappings, consent, imports, integration health, webhook receipts and audit records. Loyalty tables cover accounts, immutable rule versions, append-only ledger, tier qualifications, rewards, redemption reservations and voucher mappings. These are structural foundations; earning, redemption and operational modules remain disabled until their stages.

Status events require actor, server timestamp, source and reason and create an audit row atomically. Ledger, rules, events and audit rows reject update/delete; corrections are new records. Compound FKs prohibit a child attaching to a case, customer, batch, reward or reservation in another tenant. The migration seeds only Northside. No demo customers or owners are migrated to Supabase.

## Local evidence

At the Prompt 2 checkpoint, `pnpm test` ran 3 fixture policy tests plus 24 Prompt 2 tests. The current complete suite is recorded in RELEASE-REPORT.md. The latter run the actual SQL migration and server authorization services against PGlite (PostgreSQL compiled to WebAssembly), including two customers in one batch, a second test tenant, independent RLS, forged context, child ownership, permissions, event auditing, file lookup, formula-safe exports, expiry/revocation/refresh, identity mapping and immutability. OIDC uses the real library with signed local test tokens and mocked HTTPS provider responses. The Storage test applies the real restrictive policy to a minimal local Storage schema and proves it denies both browser roles despite a broad unrelated policy.

These results do not validate hosted database role provisioning/pooling/TLS, Supabase Auth email delivery, a real Shopify grant/refresh/logout, Storage upload/signed URL expiry, phone browser cache behavior or Vercel routing. Complete the external checks in SETUP-PROMPT-2.md before calling Prompt 2 externally verified.
