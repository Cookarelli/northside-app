## Local demonstration

Run `./scripts/preview.sh` from the project root, then visit http://127.0.0.1:3000/staff/store. The script explicitly enables development fixtures; production rejects them regardless of that environment variable.

1. **Aisles & layout:** expand one of the eight records, edit its label, sides, categories and proportional position, supply a reason and save. Reload to verify persistence. Entrance, service counter and path nodes/connections are editable. The drawing is a schematic, never a scale plan or walking route. No distance, exact shelf position or opening date is inferred.
2. **Locations:** add/edit retail, breaker or excess locators. Only active, explicitly approved retail locations can appear in a customer projection. Internal pools cannot be assigned a retail aisle or marked public. A side must belong to the chosen active aisle; move locators before removing an in-use side.
3. **Products & moves:** register family/product metadata, separately register and verify variants/SKUs/barcodes, then assign or move their locators. Provider product and variant IDs stay immutable. A locator move does not rewrite a SKU or printed code and makes no Shopify stock transfer.
4. **QR labels:** create an opaque token; optionally map an exact variant, staff placement, campaign key and product/retail-locator destination. Edit that mapping without changing the token. Download SVG/PNG; sample images visibly say **SAMPLE — NOT FOR STORE USE**. Test the displayed `/q/sample/` URL inside the staff scanner. Opening public sample URLs is deliberately disabled.
5. **Scanner:** enter `SAMPLE-BOX-BASE` or `SAMPLE-BOX-SOLDOUT`, search `basketball`, enter a registry URL, or read a saved PNG/JPEG/WebP image. Product-level codes require a variant choice. Sample stock and prices are fictional. Camera access is optional and must be requested by the user; unavailable/denied access has a manual fallback. Real phone checks remain pending.
6. **Pickup rehearsal:** create a SAMPLE order for a sample customer in the paid state, then move separately through preparing, ready and collected (or cancel before collection). Every step needs a reason and audit entry. These rehearsals do not verify money, reserve stock, send ready notices or record an actual customer handoff. Live pickup recording is explicitly rejected.
7. **Audit:** inspect the latest 100 private, append-only store changes.

The existing ignored `work/grading-preview/` database is reused, preserving grading, consignment, loyalty and break samples. Migration 008 and sample initialization run once; later visits never reset saved store edits. `work/` is local scratch data and is not deployed or committed.

## Persistence and authorization

Migration `202609120008_store.sql` adds aisles, nodes, edges, locations, registered products/variants, assignments, QR registry, pickup rehearsals and audit. It seeds only aisle numbers 1–8 with neutral labels in a live database; it does not seed a live floor plan or merchandise. Sample positions/products are created only in guarded local initialization.

Live staff requests use the existing verified session, tenant, invited membership, runtime SQL role and transaction. Owner/admin/operations can edit; read_only can inspect and download labels; customers/content editors cannot access staff store records. SQL RLS and compound foreign keys reinforce service authorization. Identity triggers freeze provider IDs, assignment variant, location pool, printed token and pickup owner/order identity. Most editors use optimistic record versions; tenant-scoped locking serializes configuration changes. Path connections are an audited serialized pair upsert. A failed or uncertain save should be followed by **Reload workspace** before retrying; the same create ID cannot create a duplicate record.

`ns.store_retail_product` and `ns.store_public_target` are fixed-tenant, fixed-search-path security-definer projections. They expose only registered product/verified variant identities, approved active retail locator fields and a campaign/destination classification. They never return QR placement, breaker/backstock positions, private audit, intake data, credentials or inventory counts. Live lookups also require publication in Storefront and replace saved display title/handle with current provider values. Barcode and SKU changes cause a staff-review error instead of silently trusting a stale mapping.

`/api/private/store` supports staff reads, edits, search, resolve and authenticated label downloads. Mutations require the existing same-origin policy. `/api/preview/store` additionally requires local fixture opt-in, nonproduction, a loopback host and the existing guarded sample actor; selecting a customer actor does not grant staff access. Both return no-store responses. PGlite is imported only after the fixture route guard.

`/scan`, `/aisles`, `/pickup`, `/q/[token]`, `/q/sample/[token]` remain 404. `/api/store` checks the relevant hard-false public flag first and returns 404. These customer routes also require a future activation implementation review; changing one environment variable or flag does not expose a staff endpoint. No customer scanner, walking route or live pickup-collection implementation is enabled in this stage.

## QR/scanner dependencies and domain

- `zxing-wasm` **3.1.4** is pinned for both QR writing and barcode reading. Its maintained [upstream implementation](https://github.com/Sec-ant/zxing-wasm) wraps ZXing-C++ and uses Zint for writing. The [writer API](https://sec-ant.github.io/zxing-wasm/docs/functions/full.writeBarcode.html) is covered by real encode/decode tests; review upgrades rather than silently changing versions.
- Reader/writer WASM are served/read locally from `public/vendor/zxing-wasm/3.1.4/`. `pnpm store:assets` verifies the installed package version and both upstream-exported SHA-256 hashes before copying. Checksums and MIT/Apache/BSD attribution are beside the assets. There is no runtime CDN fetch.
- `sharp` **0.35.4**, already a Next dependency, is now explicit for rendering the captioned SVG to PNG. The original library-generated QR symbol and quiet zone are preserved. Both complete label formats are decoded in tests.
- `NORTHSIDE_QR_ORIGIN` must eventually be the verified exact HTTPS Northside app origin, with no path/trailing slash/user information. Live label generation fails closed when it is absent. Sample URLs use `http://127.0.0.1:3000/q/sample/{token}` and cannot be generated in production. Live URLs are `{origin}/q/{token}`. Tokens are 18 cryptographically random bytes represented as 24 base64url characters; changing the destination keeps the printed token stable. Keep the domain stable too.
- Labels contain only that URL/token plus a fixed brand/sample caption. Product, variant, placement and campaign stay server-side. Destination is an enum, not a free-form redirect URL. No browser-supplied URL is handed to the encoder.

Camera scanning requests video only through [getUserMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia). It decodes capped 1280px frames locally, with a single in-flight lookup, three-second same-code suppression and a stop after the first detected code. Tracks stop on manual stop, hidden page, unmount or failed setup; a late permission response is also cleaned up. Supported live camera formats are QR, EAN-13/EAN-8, UPC-A/UPC-E, Code 128 and Code 39. Saved-image decoding uses the same library. Images stay in the browser; only code text is sent to Northside. HTTPS is needed on real phones; their `127.0.0.1` is not this Mac.

The parser accepts exact configured Northside QR URLs, known-shop `/products/{handle}` URLs with an optional numeric variant, or exact verified barcode mappings. It rejects unsupported schemes, foreign domains, user information, fragments, extra query parameters, malformed/missing variants and oversized/control-character input. The server never fetches an arbitrary scanned URL. [Shopify Shopcodes](https://help.shopify.com/en/manual/promoting-marketing/create-marketing/shopcodes) remain an optional Shopify landing mechanism; opaque Shopcodes cannot be assumed to identify a Northside cart item.

Live availability is a fresh read-only Storefront **2026-07** query for the exact registered product and variant, [SKU/barcode, price, availableForSale, currentlyNotInStock and quantityAvailable](https://shopify.dev/docs/api/storefront/2026-07/objects/ProductVariant). Unpublished/missing variants, changed mappings, non-USD money, unknown stock and backorders fail closed or stay unavailable. Online sellable quantity is not a retail shelf count. Product lookups are bounded to 100 variants and reject incomplete pagination. The future add button calls the existing `/api/commerce/cart` add action, which rechecks stock and existing commerce/break policies; it never adjusts inventory. Fixture mode and public purchase/scanner gates keep it disabled.

Staff lists are bounded: 100 nodes, 300 edges, 500 locations/products/QRs/customers, 1,000 variants, 2,000 assignments and 100 pickup/audit rows. Search returns 30 records. Larger catalogs need pagination before operational rollout. Reasons/evidence are bounded to 1,000 characters. This stage is preparation for the single Northside tenant.
